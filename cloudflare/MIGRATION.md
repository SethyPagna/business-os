# Business OS on Cloudflare (Docker-free) — Migration Guide

Started 2026-07-19. This is a genuine platform migration, not a config change —
be clear-eyed about that reading this doc. What's in `cloudflare/` right now is
a **real, tested foundation**: a schema validated statement-by-statement
against actual D1, and three working routes proven end-to-end against it
(see "What's tested" below). It is **not** a full port of the ~22-route,
Postgres/Redis/BullMQ/ffmpeg backend in `backend/`. That backend is untouched
and still works — this is an additive, parallel path you migrate into.

## Why this is a big job, honestly

Docker/Postgres path → Cloudflare path is not a lift-and-shift:

| Docker path | Cloudflare path | Why it's not just a rename |
|---|---|---|
| Express on Node, long-lived process | Cloudflare Workers, V8 isolate, request-scoped | No persistent process, no module-level connection pools, no `setInterval` background jobs |
| Postgres (`pg-native`, synchronous) | D1 (SQLite, async-only) | Every `db.prepare().get()` becomes `await db.prepare().get()`. Mechanical, but touches every query call site |
| Redis (BullMQ queues + cache) | Cloudflare Queues + KV | Different delivery/consistency model (see "Memory / caching" below) |
| Local filesystem (`business-os-data/`) | R2 only | No local disk in Workers at all — anything currently touching `fs` needs an R2 read/write instead |
| `ffmpeg` via `child_process.spawnSync` | Cloudflare Containers | Workers cannot run native binaries. Containers can (GA since April 2026) — a real Docker image, running on Cloudflare, invoked from a Worker over HTTP |
| Cloudflare Tunnel (Docker → your domain) | Not needed at all | Workers are natively served on your domain via a route/custom domain — **this removes the entire class of "Error 1033/530 tunnel" problem this conversation spent a long time on**, because there's no tunnel |

## What's built and tested in `cloudflare/`

Everything below was actually run — schema loaded into real D1, routes hit
with real HTTP requests via `wrangler dev` — not written and assumed correct.

- **`migrations/0001_init.sql`** — full 45-table schema, mechanically converted
  from `backend/src/db/postgresSchema.sql`, then validated **statement by
  statement** against a local D1 database. Two real converter bugs were
  found and fixed in the process (not schema bugs — bugs in my conversion
  script): text-typed primary keys (`import_jobs.id`, `settings.key`) were
  being forced to `INTEGER PRIMARY KEY`, and the `GENERATED ALWAYS AS
  IDENTITY` variant (used by the batch/lot tables) wasn't recognized,
  only `GENERATED BY DEFAULT AS IDENTITY` was. Both fixed and re-verified.
- **`src/lib/db.ts`** — D1 adapter matching the existing `db.prepare(sql).get/all/run()`
  shape the whole backend already uses, so porting a route is mechanical
  (add `await`, keep the SQL). Translates the same `@paramName` placeholders
  already used throughout `backend/src` to D1's positional `?` binding.
- **`src/lib/r2.ts`** — R2 via the native Workers binding.
- **`src/lib/cache.ts`** — KV-based replacement for `backend/src/runtimeCache.ts`.
- **`src/routes/settings.ts`**, **`src/routes/products.ts`** (search),
  **`src/routes/portal.ts`** (catalog search) — ported and verified:
  ```
  PUT  /api/settings/store_name  -> {"key":"store_name","value":"Leang Cosmetics"}
  GET  /api/settings             -> {"store_name":"Leang Cosmetics"}
  GET  /api/products/search?query=glow        -> correctly matched via brand column
  GET  /api/products/search?category=Makeup   -> correctly matched via faceted filter
  GET  /api/portal/catalog/products/search    -> the exact route that returned 500
                                                  under the Docker/Postgres password
                                                  mismatch — 200 here, correct data
  ```
- **`src/routes/sales.ts` (POS checkout)** — the highest-stakes route in the
  app (money + inventory correctness), so it got the most scrutiny. Real,
  tested atomicity, not a hand-wave:
  - `POST /api/sales` validates stock as a plain read *before* building any
    writes (D1's `batch()` can't branch mid-batch — see `lib/db.ts`), then
    writes the sale header, then atomically writes sale_items + branch_stock
    deduction + inventory_movements as one `db.batch()` call.
  - **Tested the success path**: 3 units sold, subtotal/total/change
    calculated correctly (USD + KHR), stock correctly deducted (40 → 37).
  - **Tested the failure path directly** (not assumed): requested 100 units
    against 5 in stock → rejected with 409, then verified — not assumed —
    that `sales`, `sale_items`, and `inventory_movements` all show **zero**
    rows and `branch_stock` is **unchanged**. No partial writes.
  - Found and fixed a real dialect bug while porting: the original
    `deductBranchStock` uses `GREATEST(0, ...)`, which is Postgres syntax —
    SQLite/D1 has no `GREATEST()` function at all (it would be a hard
    syntax error, not a subtle bug). SQLite's `MAX()` accepts multiple
    scalar arguments and does the same job; used that instead.
  - `GET /api/sales/:id` (receipt display) tested with both a real sale and
    a 404 case.
  - **Scoped deliberately**: the original also supports product batch/lot
    FIFO allocation, membership point redemption, and delivery tracking.
    Not ported this pass — noted honestly below, not silently dropped.

- **`src/queue.ts`** — Cloudflare Queues consumer pattern for import/media
  jobs, replacing BullMQ. The dispatch/ack/retry plumbing is real; the actual
  row-by-row import logic and the ffmpeg Container hand-off are sketched
  with detailed comments, not implemented (see "What's not done" below).

Run it yourself: `cd cloudflare && npm install && npm run migrate:local && npm run dev`,
then hit `http://localhost:8787/health`.

## Answering your specific questions

### "How search is divided and column search"

Nothing about the search logic changes. `backend/src/routes/products.ts`'s
search was already SQLite-native: multi-column `OR`-joined `LIKE` matching
using `lower(...)` on `name`, `sku`, `barcode`, `brand`, `category`,
`supplier`, combinable across multiple search terms with AND/OR, plus
separate exact-match `lower(trim(col)) = @value` faceted filters for
`brand`/`category`/`unit`/`supplier`. That's copied byte-for-byte into
`cloudflare/src/routes/products.ts` — D1 is SQLite, so it just runs. The
schema's supporting indexes (`idx_products_name_lower_pg`, `_brand_lower_pg`,
`_category_lower_pg`, etc. — all `lower(column)` functional indexes, plus
partial unique indexes for conditional dedup) converted the same way, index
type stripped (`USING btree` has no SQLite equivalent, SQLite only has one
kind), everything else kept.

### "Memory" (caching)

`backend/src/runtimeCache.ts` is a Redis-backed short-TTL (~20-30s)
read-through cache with prefix-based invalidation (`deleteByPrefix` does a
Redis `SCAN`+`DEL`). `cloudflare/src/lib/cache.ts` replaces it with KV, with
one real behavioral difference worth understanding rather than papering
over: **KV has no atomic "delete everything starting with X."** Redis's
prefix-scan-delete pattern doesn't have a clean KV equivalent at the same
cost. The fix isn't a workaround, it's a better-fit pattern for KV: a
**version counter per cache namespace** (`versionedKey`/`bumpVersion` in
`cache.ts`) — bump the version on any write that should invalidate reads,
fold the version into every read's cache key, and stale entries just expire
on their own TTL instead of needing to be found and deleted. Cheaper and
avoids KV's list-then-delete eventual-consistency window entirely.

### R2

Already R2 in the Docker path, but reached through the S3-compatible API
(access key, secret, endpoint, request signing) because a Node container has
no other way in. A Worker bound directly to the bucket (`[[r2_buckets]]` in
`wrangler.toml`) skips all of that — `env.ASSETS` *is* the bucket, no
credentials to generate, rotate, or (as happened earlier in this
conversation) paste into a chat by accident.

## What's not done (the honest remainder)

- **~18 of 22 route files** not yet ported: `auth.ts`, `inventory.ts`,
  `returns.ts`, `branches.ts`, `customTables.ts`, `importJobs.ts`,
  `notifications.ts`, `users.ts`, `organizations.ts`, etc. Same technique as
  `products.ts`/`settings.ts`/`sales.ts` throughout — this is real work, not
  a fundamentally different problem, but it's dozens of route handlers and
  it would be dishonest to claim it's done without actually doing and
  testing each one the way the four above were tested.
- **Within `sales.ts` itself**: product batch/lot FIFO allocation
  (`backend/src/productBatches.ts`'s `allocateProductBatches` — picks which
  specific expiry-dated lot to sell from), membership point redemption, and
  delivery-order tracking are not ported. The core checkout — pricing, tax,
  discount, dual-currency totals, branch-scoped stock deduction, atomic
  writes — is, and is tested (see above).
- **Auth/sessions**: `backend/src/sessionAuth.ts` uses Node's `crypto`
  module directly. Workers' `nodejs_compat` flag (already on in
  `wrangler.toml`) supports much of `node:crypto`, but this needs its own
  verification pass before relying on it for password hashing / session
  tokens — security-sensitive code deserves more than "probably fine."
- **Import jobs**: the queue plumbing exists; the actual CSV/ZIP
  row-processing logic (currently in `backend/src/services/importJobs.ts`)
  isn't ported. Also needs re-architecting around Workers' per-invocation
  CPU-time limit — this app allows imports up to 2048MB, which one Docker
  process could chew through in one long-running call. On Workers that
  needs chunking: process N rows, persist progress, re-enqueue a
  continuation message.
- **ffmpeg / video optimization**: needs a Cloudflare Container (GA since
  April 2026 — a real Docker image with ffmpeg, running on Cloudflare,
  callable from a Worker over HTTP). Sketched in `src/queue.ts`, not built.
  Worth knowing this app already treats ffmpeg as optional
  (`backend/src/fileAssets.ts` degrades gracefully to `"ffmpeg unavailable"`
  if the binary is missing) — so this can genuinely be a phase-2 item
  without blocking everything else.

## Performance, at each layer that changed

- **D1 reads**: Cloudflare runs read-only replicas of D1 near where
  requests come from and serves reads from the nearest one; writes still go
  to one primary. This is a real, structural latency improvement over the
  Docker path's single Postgres container the whole world (or at least
  wherever your tunnel connects from) had to reach — but it means a read
  immediately after a write from a *different* edge location can be
  momentarily stale. Use D1's Sessions API (`withSession`) for
  read-your-writes consistency on flows where that matters (e.g., showing a
  receipt right after creating the sale); not wired up yet in
  `cloudflare/src/lib/db.ts`.
- **D1 writes / round trips**: `db.batch()` isn't just about atomicity —
  batching statements into one call is a real latency win, since each
  non-batched `await db.prepare(...).run()` is its own network round trip
  to D1. `sales.ts`'s checkout deliberately batches every item's
  sale_items + branch_stock + inventory_movements writes into a single
  `batch()` call rather than looping with individual `await`s.
  `products.ts`'s search still does two separate reads (count, then page) —
  a reasonable target for a follow-up `batch()` pass once you have real
  query volume to profile against, not a change to make blind.
- **Caching**: `products.ts`'s search result is KV-cached for 20s the same
  way the Redis version cached it for ~20-30s (see "Memory" above) — main
  defense against repeat identical searches hammering D1, same as it was
  against Postgres. The `versionedKey`/`bumpVersion` pattern does a KV read
  before every cache read to resolve the current version — for very
  high-traffic routes, consider caching the version number itself briefly
  in-memory per Worker invocation rather than fetching it from KV every
  request.
- **Workers CPU/memory**: no per-container memory ceiling to size or
  monitor anymore (the Docker path's Postgres/Redis/app containers each had
  memory limits to reason about) — a Worker gets 128MB and a short CPU-time
  budget *per request*, generous for typical API/CRUD work but a hard wall
  for anything CPU-heavy in one request (bulk CSV parsing, image
  transforms) — exactly why the import/media queue consumers in
  `src/queue.ts` exist as separate, chunked invocations instead of doing
  that work inline in a request handler.
- **R2**: no performance change to call out beyond the credential
  simplification already covered above — R2's read/write characteristics
  are the same whether reached via S3-compat or a native binding; the
  binding is simpler and safer, not faster.

## Frontend compatibility

`frontend/` is untouched (confirmed by diff), and none of the above
requires frontend changes to keep working *once the ported routes have
auth*. Checked `frontend/src/api/http.ts` (the central fetch client): plain
JSON `fetch()` with `credentials: 'include'` for cookie-based sessions —
this works against a Hono/Workers backend exactly as it does against
Express, **once session auth is ported** (right now nothing in
`cloudflare/` checks auth or sets a session cookie, so the frontend's login
flow has nothing to talk to yet on this path — don't point it here before
that exists). No CORS headers are configured in the Workers app yet — if
the deployed Worker ends up on a different origin than the frontend, add
Hono's CORS middleware; if it's mapped to the same domain (a Workers Route
can do this), it's same-origin and none is needed.

## The bat files question — direct answer

**As long as you're running the Docker path (which still works and is
untouched), keep all of it.** Nothing in `run/` or `ops/` changed or should
change for that path to keep working.

**Once/if you fully cut over to this Cloudflare path**, these become
unnecessary — replaced by `wrangler` itself, which already does what they did,
built into Cloudflare's own CLI:

| Becomes unnecessary | Replaced by |
|---|---|
| `run\docker\install.bat`, `start.bat`, `stop.bat`, `update.bat` | `wrangler deploy` (Cloudflare handles process lifecycle, restarts, scaling — there is no "start/stop a container" step) |
| `run\docker\doctor.bat`, `verify-tunnel.bat` | Not applicable — no tunnel, no local Docker engine to diagnose |
| `run\docker\backup.bat`, `restore.bat` | `wrangler d1 export` / `wrangler d1 execute --file` (D1 has its own backup/restore, and Cloudflare also does automatic point-in-time recovery on paid plans) |
| `run\docker\rotate-cloudflare.bat` | Not applicable — no tunnel token to rotate |
| `run\docker\release.bat`, `run\build-release.bat` | `wrangler deploy` — no image to build, no portable folder to assemble |
| `run\start-server.bat`, `run\stop-server.bat` | `wrangler dev` (local) / already deployed and always-on (production — Workers don't get "stopped") |
| `ops\scripts\powershell\docker-release.ps1` (the entire 1,100+ line orchestrator this conversation spent most of its time fixing) | Not needed. `wrangler.toml` + a handful of `npm run` scripts (already in `cloudflare/package.json`) cover what it did, because Cloudflare's platform now does the orchestration Docker made you do yourself. |

`run\setup.bat` and `run\cloudflare-origin.bat` also stop applying (no local
backend to bootstrap, no tunnel ingress to publish). `run\verify-local.bat`
and `run\full-automation.bat` partially still apply (typecheck/lint), minus
the Docker build/deploy steps.

None of this is deleted yet — the Docker path is still real and working.
Delete it only after you've actually cut over and confirmed the Cloudflare
path handles your real traffic, not before.
