# Browser end-to-end suite (Playwright)

Sixteen spec files drive the **built** app in three browsers: desktop Chromium, a
Pixel 7 Chromium and an iPhone 13 WebKit. They exist to catch the error classes
this project has actually shipped before — blank page, runtime error, glitch,
slowness, another cashier's data on my screen — at the only layer where those
classes are observable at all.

A tenth spec, `e2e/system/pos-sale.spec.ts`, is opt-in and answers the one
question the others structurally cannot: does a sale rung on the till
actually survive the round trip through the real Worker and the real database.

Nothing here can reach production. Every URL is loopback.

---

## Run it

```bash
cd frontend
npm run build          # the suite tests dist/, not the dev server
npm run test:e2e       # all three projects
```

| script | what it does |
| --- | --- |
| `npm run test:e2e` | the whole Tier "app" suite, all three projects |
| `npm run test:e2e:fresh` | `npm run build` first, then the suite |
| `npm run test:e2e:ios` | the iPhone 13 WebKit project only |
| `npm run test:e2e:system` | Tier "system" — needs a local Worker, see below |
| `npm run test:e2e:ui` | Playwright's watch/inspect UI |
| `npm run test:e2e:report` | open the HTML report from the last run |

This machine is shared with other sessions. A run that competes with a dozen
other browsers is slower per action, not wrong — but it can exhaust the
runner's waits. `E2E_WORKERS=2 npm run test:e2e` buys the headroom back
without changing a single assertion. (Measured: one run lost 5 ios-webkit
tests purely to CPU starvation; every one of them a click on an element
Playwright had already found and was waiting to settle, and every one passed
immediately when re-run alone.)

One file, one project, one test:

```bash
npx playwright test storefront-pager                     # one file
npx playwright test scanner --project=ios-webkit         # one file, one browser
npx playwright test -g "boots to a login form silently"  # one test by name
```

The e2e suite is deliberately **not** part of `npm run test:utils`. That chain
is the fast unit gate and must stay fast; it also must not need a browser.
`tsconfig.json` excludes `e2e/`, and the specs have their own typecheck:

```bash
npx tsc --noEmit -p tsconfig.e2e.json
```

Browsers live in `%LOCALAPPDATA%\ms-playwright`, outside the repository.
Install them once with `npx playwright install chromium webkit`.

Output — `e2e-report/`, `test-results/`, `playwright/.cache/` — is gitignored.
Traces, videos and screenshots are retained **on failure only**, so a green run
writes nothing heavy.

## The two tiers

### Tier "app" — default, deterministic, no backend

`e2e/*.spec.ts`. `e2e/server/fixtureServer.mjs` serves the real `frontend/dist`
plus committed `/api` fixtures on two loopback origins:

- `http://127.0.0.1:4318` → the **admin** shell
- `http://127.0.0.2:4318` → the customer **storefront**

Two origins because `src/app/pathRouting.ts` routes `/` by HOSTNAME, exactly as
`admin.leangbeauty.com` and `leangbeauty.com` do in production.

The fixtures in `e2e/fixtures/` are generated by `node
e2e/fixtures/build-fixtures.mjs`, and every field is copied from the Worker
route that produces it (`cloudflare/src/routes/portal.ts` `buildPortalConfig`,
`buildPortalMeta`, `buildPortalCatalog` + `attachPortalStockStatus`, and
`auth.ts` / `settings.ts` / `sales.ts` / `runtime.ts` for the admin ones). The
portal product rows drop `stock_quantity`, `low_stock_threshold` and
`out_of_stock_threshold` and add `stock_status` — reproducing that removal is
the point, because it is the storefront's security boundary.

The catalogue is 137 products with unique names, so one row is one card and the
page counts are exact (7 pages at 20, 3 at 50, 2 at 100).

Unknown `/api` paths answer **404** `{ code: 'e2e_unmocked' }` on purpose, not
an empty 200, so a new boot dependency shows up as a failing test instead of an
empty screen.

Sign-in goes through the real login form and the real `POST /api/auth/login`,
and the fixture server sets the real session cookie (`bos_session`). Accounts:
`admin`, `cashier_a`, `cashier_b` (any non-empty password).

### Tier "system" — opt-in, real Worker, real D1

`e2e/system/*.spec.ts`, collected only with `E2E_SYSTEM=1`; in that mode the
fixture `webServer` is suppressed so it cannot shadow the real one. Nothing is
stubbed: the real bcrypt check, the real `POST /api/sales`, the real D1.

One-time, then once per machine reboot:

```bash
cd cloudflare

# 1. Schema. NOT `npm run migrate:local` -- see the note below.
node scripts/apply-local-migrations.cjs --persist-to "$LOCAL_D1"

# 2. The Worker. NOT port 8787: that is the shared worker-dev server other
#    sessions own. It also provisions the pinned organization on first boot,
#    which is why it starts BEFORE the seed.
npx wrangler dev --local --port 4319 --ip 127.0.0.1 --persist-to "$LOCAL_D1"

# 3. Data: one administrator cashier, two canonical branches, three priced
#    products with shop stock, and a reset of the login limiter's counters.
node scripts/seed-e2e-local.cjs --persist-to "$LOCAL_D1"

cd ../frontend
npm run test:e2e:system
```

`$LOCAL_D1` must be a SHORT path — `C:\Users\<you>\AppData\Local\Temp\bos-e2e-d1`
is what this was measured with. The default `cloudflare/.wrangler/state` inside
a deep worktree exceeds the Windows path limit and miniflare fails with
`SQLITE_CANTOPEN` before the first statement runs.

One origin is enough: `wrangler.toml` serves `../frontend/dist` as `[assets]`
with `run_worker_first = ["/api/*", …]`, and `src/app/pathRouting.ts:106`
treats `127.0.0.1` as the admin host.

**Why `npm run migrate:local` is not used.** On wrangler 4.116.0 it cannot
apply this project's migration set at all: it concatenates every pending file
into one local query and dies in its own result aggregation with
`too many terms in compound SELECT: SQLITE_ERROR`. Measured — the first run
applied the schema through 0097 and recorded 97 rows, and re-running with 64
files still pending failed identically and applied nothing, so it does not
converge by repetition. `scripts/apply-local-migrations.cjs` applies the same
files, in the same order, one transaction each, into the same `d1_migrations`
table. It is local-only by construction: no network code, no `--remote`, no
credential.

**Why one browser.** Running the system spec on all three projects at once
fails the second and third with the server's own words, "Too many login
attempts for this account." That is the real limiter working as designed
(`routes/auth.ts:56`, 8 per account per 15 minutes; `:54`, 20 per IP), and the
answer is not to raise it for tests. This tier asks "does the whole stack
work", which is a per-stack question; the per-engine questions live in tier
"app", which needs no login at all. Override with `E2E_SYSTEM_PROJECT`.

**Why the seeded cashier is an administrator.** `lib/deviceTrust.ts:31`
`requiresDeviceApproval()` gates every non-administrator account behind a
per-device approval, so a cashier-role seed answers a correct password with
`deviceApprovalRequired`. The device gate is a real behaviour that deserves
its own spec; it is not this one.

What the one system spec proves, in one flow: a real sign-in reaches the
shell → the seeded product reaches the till from D1 → one tap puts it in the
cart (positive control: the cart must stop reading "Cart is empty") → "Exact
$" then "Complete Sale" → `POST /api/sales` creates **exactly one** sale →
that sale carries the right total, status, item, quantity, cashier and branch
→ shop stock drops by exactly one → and the receipt number is visible on the
Sales page. If the till refuses instead of selling, the refusal toast is read
back into the failure message rather than left to expire.

Every spec file opens with a header naming what it proves, the incident class it
guards, and the command that runs just that file. Every assertion carries a
comment naming the wrong implementation it would catch.

## Known-noise quarantines

`support/harness.ts` exports three named **product** allowances (`KNOWN_*`).
Each was measured, is scoped as narrowly as the evidence allows, is owned by
one of the red tests above, and carries delete-me instructions. Every
**other** page error and `console.error` still fails every spec.

It also carries one **harness** allowance,
`FIXTURE_BLOCKED_FETCH_ARTIFACT`. Under parallel load the fixture server
occasionally drops a request, and WebKit reports that as a page-level
"… due to access control checks." that no application code can catch. It is
scoped to two paths (`/sw.js`, `/health`) on the two loopback origins, and
both of the app's `/health` call sites (`src/api/http.ts:1022`,
`src/api/systemRuntime.ts:106`) are inside `try/catch`. The obvious
explanation — that WebKit rejects the probe's
`redirect: 'manual'` + `credentials: 'include'` — was tested directly and is
**wrong**: plain, credentialed, manual-redirect and the exact combination
`http.ts` sends all returned `200`/`basic` from a quiet WebKit page.

## A finding with no spec of its own

`support/session.ts escapeSessionQuarantine()` recovers from, and prints a
`[finding]` line for, the full-screen **"Sign-in changed"** lock
(`App.tsx:1683`) appearing on a *signed-out login screen*, reading "Another
account is signed in. Sign back into the original account in the other tab,
then retry." Observed once on a first sign-in into a fresh browser context,
with no other tab. `AppContext.tsx:983` computes

```ts
const sameActor = !!user?.id && String(nextUser?.id) === String(user.id) && …
```

so when `user` is null the first operand decides, and `:985` reports
`'different-account'` without comparing anything. Retry re-runs the same
comparison and can never succeed; only Reload escapes. There is no spec for
it because it has no deterministic reproduction yet — it needs the login
result object to be dropped, which is a timing window, not an input.
