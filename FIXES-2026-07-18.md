# Fix Log — 2026-07-18

## Root cause of "Error 1033" / "Error 530"

`ops\scripts\powershell\docker-release.ps1` generates `ops\runtime\docker-release\docker-release.env`
for the Docker release runtime, but it never wrote `CLOUDFLARE_ACCOUNT_ID` or
`CLOUDFLARE_TUNNEL_ID` into that file. Those two values only ever existed in
`backend\.env`, which is written by the separate source-checkout `run\setup.bat`
flow — a script normal Docker-only users are told *not* to run
(`run\README.md`: "support-only source checkout"). On a Docker-only install,
`backend\.env` never exists, so every Cloudflare tunnel script
(`rotate-cloudflare-tunnel-token.ts`, `update-cloudflare-tunnel-origin.ts`) had
no account/tunnel ID to work with. Separately, `update-cloudflare-tunnel-origin.ts`
only read `backend\.env` (unlike the rotate script, which read both env files),
so even setting the values in one place didn't guarantee the other script saw them.

On top of that, `run\docker\doctor.bat` — documented as diagnosing "Docker, ports,
local image bundles, Cloudflare, database, workers, and storage" — never actually
checked the Cloudflare Tunnel at all. So there was no path in the tooling that
would ever tell you *why* the tunnel was down; `Start Business OS.bat` would
report success even when the tunnel had zero active connections.

## What changed

- `ops\scripts\powershell\docker-release.ps1`
  - `Ensure-Env` now populates `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_TUNNEL_ID`
    in the Docker release env file (falls back to `backend\.env`, then to the
    account/tunnel IDs already used as defaults elsewhere in the repo).
  - Same fix applied to the portable-release-kit env builder used by
    `run\build-release.bat` / `run\docker\release.bat`.
  - `Invoke-Doctor` now actually runs a Cloudflare Tunnel check (new
    `Invoke-CloudflareTunnelDoctor` helper) instead of skipping Cloudflare
    entirely.
  - `Invoke-Start`'s startup warmup step now runs that same diagnostic on
    failure instead of printing a generic warning and moving on.
- `ops\scripts\runtime\cloudflare\update-cloudflare-tunnel-origin.ts`
  - Now reads both `backend\.env` and `ops\runtime\docker-release\docker-release.env`
    (previously only the former), matching the rotate script.
- `ops\scripts\runtime\cloudflare\verify-cloudflare-tunnel.ts` (new)
  - Checks, in order: account/tunnel/API-token config presence, the tunnel
    connector token file (non-empty), Cloudflare's API for an active connector
    (the literal cause of Error 1033), the ingress routes for your hostnames
    (the literal cause of Error 530), and — if the `docker` CLI is available —
    the `cloudflared` container state and recent logs.
- `run\docker\verify-tunnel.bat` (new) — standalone wrapper for the check above.
- `run\README.md`, `run\docker\README.md`, root `README.md` — documented the
  new command and added a concrete "Error 1033 / 530" troubleshooting section
  and a source-checkout new-machine setup path.

## What I could NOT do from here, and why

This was fixed and reviewed statically (code read, syntax checks, dry runs) —
I do not have Docker, and my network access is restricted to a short allowlist
that does not include `api.cloudflare.com`, so I could not actually bring the
tunnel up or run `docker compose` myself to confirm end-to-end.

**One step is still yours to run, on a machine with real internet access:**

```
run\docker\rotate-cloudflare.bat
```

This fetches the actual Cloudflare Tunnel *connector* token (a long, separate
secret from the API token you pasted — cloudflared authenticates with this,
not with the API token) and writes it to
`ops\runtime\docker-release\secrets\cloudflare-tunnel.token`. Nothing pasted
into this chat included that value, so this is the one thing I couldn't
pre-fill for you.

Then:

```
run\docker\start.bat
run\docker\verify-tunnel.bat
```

`verify-tunnel.bat` will tell you plainly if anything is still wrong and why.

## Also fixed this session: broken/dead run\ scripts

A full static audit (syntax-checked all 85 ops/scripts .ts files, all
backend/frontend TS/TSX, all 3 .sh files; balance-checked all .ps1 files;
verified every file reference in every .bat/.ps1/package.json actually
resolves) turned up more concrete bugs beyond the tunnel issue:

- **`run\stop-server.bat` did not stop the actual running app.** It targeted
  `ops\docker\compose.scale.yml` / `ops\runtime\docker-scale.env` — a retired
  compose stack — while `Start Business OS.bat` runs the current
  `compose.release.yml` stack. Running it left the real containers running
  in the background while reporting success. There was also no `Stop` action
  anywhere in `docker-release.ps1` for it to call. Fixed: added a real
  `Stop` action, added `run\docker\stop.bat`, and `stop-server.bat` now
  forwards to it.
- **`run\start-server.bat` was ~540 lines of unreachable dead code.** It
  unconditionally forwarded to `run\docker\start.bat` and exited near the
  top; everything below (PM2 launch, host cloudflared, Tailscale funnel)
  could never run. Trimmed to a short, honest forwarder.
- **Two fully orphaned scripts removed**: `ops\scripts\powershell\start-runtime.ps1`
  and `tailscale-health-monitor.ps1` — both only ever called from the dead
  code above, confirmed via grep across every script in the repo.
- **`ops\scripts\powershell\clear-stale-node-processes.ps1` had hardcoded
  references to an unrelated sibling project** (`../LEARN`), making it a
  silent no-op for anyone without that other project checked out next to
  this one. Removed the cross-project coupling.
- `run\setup.bat` had a stale PM2 message pointing at the now-removed
  PM2 mode in start-server.bat; removed.



The `ops\docs\` reference/audit files (multi-hundred-KB session logs,
