# Sample evidence fixtures

Generated by `../build-sample.mjs` -- do not hand-edit these files; edit the
generator and re-run it (`node ops/product-verification/fixtures/build-sample.mjs`
from the repo root) so `sample-input.json`, `sample-manifest.json`, and this
directory stay in sync.

One `<productId>.json` per product in `sample-input.json`, shaped for
`providers/mockProvider.mjs`:

```json
{ "name": [SearchHit, ...], "barcodes": { "<barcode>": [SearchHit, ...] } }
```

## Where the evidence came from

- 15 products (ids 195, 204, 498, 660, 1058, 1237, 1373, 1461, 1462, 1464,
  1522, 1528, 2361, 2827, 3549) replay a genuine prior web-verification pass
  recorded in `../barcode-web-evidence.json` (dated 2026-09-02), each given
  one additional, independently-domained name source found via a fresh web
  search in this session (that file records only one source per product;
  this tool requires two independent domains before it will call a name
  confirmed -- see the main README's "why two domains").
- 15 products (ids 6032-6044, plus 6066/6075/6093/6099-range picks) replay
  `../prior-recertification-6032-6104.json`, a genuine prior recertification
  pass over ids 6032-6104 -- `official_source_url` / `independent_source_url`
  become name hits, `barcode_source_url` becomes a barcode hit, verbatim.
  No fresh searching was needed for this half of the sample.
- 1 product (id 342, Bobbi Brown Skin Fluid N-012) demonstrates a genuine
  `barcode_changed` case pulled directly from `tmp/latest-data-reconcile/
  product-reconciliation.json`'s variant records: the source import row
  recorded barcode `716170241333`; the live, fuzzy-name-matched current
  product record instead carries `07161702412`. Both numbers are real.

## The one gap in the real data, and how it's covered

An exhaustive search (documented in the Section 7 report) found **zero**
products in the available real artifacts with two genuinely different
barcodes currently on record for the same product -- the live `products`
table has exactly one `barcode` column, and no alias-tracking data (the 73
row prior recertification pass's own `barcode_aliases` column included) has
ever captured a second real value for any product. Two products (1461,
1462) come close: their *source* spreadsheet cell held two 6-digit tokens
separated by a space, which this fixture set models as two separate barcode
entries -- real, but both too short to be a valid GTIN either way.

To still exercise `multi_barcode` (>=5 rows) and `barcode_changed` (>=3
rows) per the plan's acceptance bar, `build-sample.mjs` attaches a
**constructed** second value to 3 otherwise-real products (195, 498, 6033)
and a constructed prior-verification snapshot to 2 otherwise-real products
(6034, 6075). Every constructed value is checksum-valid (built and verified
against `lib/barcode.mjs`'s own `gtinCheckDigitValid`, the same function
`reconcile.test.mjs` checks against 15 real barcodes) but is explicitly
**not** claimed to be a real second barcode for that product -- each
constructed row is tagged `constructed` in `build-sample.mjs` and in
`sample-manifest.json`'s `groupTags`.
