# Inventory Check marks (read switch `ic_marks`, default OFF)

Spec: `Records/Design/2026-11-20/SPEC-ic-as-products-view.md` section 1 and slice S0a. Code: `cloudflare/src/lib/inventoryCheckMarks.ts`, `cloudflare/src/routes/inventoryChecks.ts`.

A **mark** is the latest count of a product at a branch: `[productId, t, s]`, `t` = the count's `updated_at` in epoch milliseconds, `s` = 1 OK, 2 Differs. The latest count is the one rule of the overlay's `COUNT_ENTRIES_SQL`: newest `updated_at`, then `session_id`, inside the viewer's organisation, with the item's branch equal to its session's. No quantity, stock, cost, price or person is in a mark. An event's **tag** is `fnv1a32` of `id|actor_id|request_id|created_at` (8 hex).

With `ic_marks` OFF the three routes answer 404 `not_found` and `capabilities.marks` is absent from `/list` and `/overlay`. All routes need `canView` (else 403 `inventory_check_view_required`), a positive `branchId` (else 400 `inventory_check_invalid_query`), and single-valued parameters.

| Route | Answer |
|---|---|
| `GET /marks?branchId&page[&have]` | `{format, page, buckets, cursor, tag, top, hash, rows: [[id,t,s]]}`; with `have` equal to `hash`: the same without `rows` plus `unchanged: true`. Every product id of the page range is seeked, active or not. A page holds 1,000 product ids in both profiles (`inventoryMarksPageIds`). `hash` is `fnv1a32` over `format:page:cursor:tag` (the format, the page number, the page's cursor event id and that event's tag), not over the rows: the rows of a page change only through events, and every event moves the cursor or the tag. The cursor and the rows are read in one `db.batch`. Cached (Cache API, key has org, branch, page, format, epoch) for `inventoryMarksSnapshotCacheSeconds`; every request validates the cached page with one call and serves it only while `cursor <= top`, its cursor event still has its tag, and `top - cursor <= inventoryMarksCatchUpMaxEvents / 2`. |
| `GET /marks/changes?branchId&since&tag` | `{rebuild: true, top}` when `since > top` or the event at `since` has another tag; else `{cursor, tag, top, more, exact, marks: [[id,t,s]] (s = 0: no count, remove), waiting?: [[sessionId, [productId...]]]}`. At most `inventoryMarksChangesPageEvents` events; the walk stops before the event that would push `P + L` over `inventoryMarksTouchedMax` (P: touched products, one for the first event naming it; L: the member count of each pending legacy session, charged once; waiting ids and NULL-product events cost 0), but always walks the first event; `cursor` is the last event walked. `waiting` lists every walked in-scope session that holds an approval, with the FULL list of its waiting products (a decided approval answers `[]`); the device replaces its entry for that session. It is computed for every viewer and removed at serve time, from the signed-in actor of the request, unless the viewer has the stock field and Fix stock. The last batch of the read ends with the newest event: `exact` is true only when no event was written since call 1; otherwise `more` is true and the device publishes nothing until a chain ends with `more = false`. An approval with no stored line set (`legacy`, pending only) is answered by the engine's own rule over its items. |
| `GET /marks/pending?branchId[&afterAt&afterId]` | `{cursor, tag, sessions: [[sessionId, [productId...]]], next: {afterAt, afterId} \| null}`: the waiting lines of the next `inventoryMarksPendingPageApprovals` approvals, newest first, by session (an approval whose open lines all landed answers `[]`). 403 `inventory_check_fix_stock_required` for any other viewer. Never cached. |

Every non-GET Inventory Check answer below 400 (or 500+) also broadcasts channel `inventory_checks` with `{branchId}` (best effort, whatever the switch says; a broadcast is not a read).

Limits (`getPlanLimits`): `inventoryMarksPageIds`, `inventoryMarksSnapshotCacheSeconds`, `inventoryMarksChangesPageEvents`, `inventoryMarksTouchedMax`, `inventoryMarksCatchUpMaxEvents`, `inventoryMarksPendingPageApprovals`, `inventoryMarksPollSeconds`.

The branch check of the three routes is the check of the existing count routes: 403 `inventory_check_view_required` without `canView`, `branchId` a positive safe integer (else 400 `inventory_check_invalid_query`), the organisation in every SQL text, no per-actor branch grant.

**When the changes read walks a pending session's line set (A1d).** `/marks/changes` walks `json_each(line_set_json)` of a pending approval, and sends that session's waiting list, only when the answer's events include one that can change the set: an event of action `create` (the submission; also every other session creation, which is harmless), or an event whose `after_json` carries `approval` (`decides` in `EVENTS_SQL`; a malformed `after_json` counts as deciding). A plain `observe` never walks. D1 bills one row per key of the walked set, so a 500-line submission answered in a chain of reads walks its 500 keys once (the read that holds its `create` event) and not again for the `observe` events that follow; the cost formula gains `+ K`, the keys of the walked pending sessions. The device keeps each pending session's list until an answer carries a new one or the session leaves pending (an answer for a decided session carries `[]`). The events the writers can produce (the table's action column is the events table's CHECK list: create, observe, close, resume), and whether each changes a pending session's waiting set: the two submission writers (plain and lots, tasks included, `ic_wired` either way) record one `create` event in the batch that inserts the approval and its line set: yes; their per-line `observe` events (state, counted_quantity, no `approval`): no, the set is fixed by that insert; supersede events (`SUPERSEDE_EVENTS_SQL`, `observe`, `approval` = the old approval's new status, one per superseded line, naming the OLD session): yes; line decisions (reject, reopen, modify), approval landings, approve, reject, close, takeover and the `-end` event (`observe`, `approval` in `after`): yes; an ordinary item observation in an open session and an Undo's "count taken back" (`observe`, state and counted_quantity only): no, they touch items of sessions that hold no approval row (only the two submission writers insert approvals, into sessions created closed); `close` and `resume` (session patch, task and pickup closes, Set-closes-Issue): no, they write the session row and never the approval row (a submission session is created closed, so `close` needs status open and is refused, `resume` is refused as final; Issues, tasks, pickups and Set sessions hold no approval), and an unrecognised action would count as yes. `cloudflare/scripts/test-inventory-check-marks-pure.cjs` keeps this true: its registry finds every statement in `cloudflare/src` that inserts into `inventory_check_approvals` or updates its `line_set_json`, `status`, `applied_json`, `superseded_json` or `line_decisions_json`, and requires that the unit holding it (or every unit that uses it, for a statement builder) also writes such an event; a new writer without the marker turns it red.
